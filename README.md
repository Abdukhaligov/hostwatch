# hostwatch

Панель здоровья Windows-компьютеров в локальной сети. На каждом ПК работает
маленький агент, раз в секунду он отправляет данные на сервер, а сервер
показывает их в браузере.

**Что видно по каждому ПК:** метка, имя, пользователь, IP и MAC, CPU, память,
диски, сетевой трафик, аптайм и статус:
- **ACTIVE** — за компьютером работают;
- **IDLE** — 2 минуты без мыши и клавиатуры (только в рабочее время);
- **OFF-HOURS** — сейчас нерабочее время, простой не считается;
- **OFFLINE** — 30 секунд нет отчётов.

Компьютеры с проблемами (CPU ≥90% дольше 2 минут, память ≥90%, на диске
меньше 10% свободного) показываются первыми. На вкладке **IDLE** видно,
сколько каждый ПК был активен и сколько простаивал за день (история ~2 месяца, выбор даты).
Там же строка **EXPORT CSV** выгружает эти логи за выбранный период: **PER DAY** —
итоги по каждому ПК за каждый день (active, idle и offline — рабочее время без отчётов), **SEGMENTS** — все отрезки active/idle/off-hours
с началом и концом (`GET /api/idle/export?kind=summary|segments&start=YYYY-MM-DD&end=YYYY-MM-DD`).

На карточке рядом с IP есть две кнопки подключения:

- **RDP** — скачивает `.rdp` и открывает удалённый рабочий стол (Windows —
  `mstsc`, Mac — Microsoft Remote Desktop). Это **новая** сессия: пользователь,
  сидящий за ПК, будет выкинут. Нужен включённый Remote Desktop (Windows Pro+;
  Home входящий RDP не умеет) и учётные данные.
- **SHADOW** — подключение к **текущей** сессии пользователя (RDP shadowing):
  видишь и управляешь его экраном без перелогина — то, что нужно для помощи
  сотрудникам. Скачивает `.cmd` с `mstsc /shadow:<id> /v:<ip> /control`.

Условия для SHADOW:

- запускать `.cmd` надо с **Windows** (у Mac shadow не поддерживается);
- ты должен быть **админом на целевом ПК** (обычно через доменную учётку/GPO);
- на целевом ПК включён Remote Desktop и открыто правило брандмауэра для
  теневого подключения — установщик делает это сам;
- **пользователь за ПК увидит запрос «разрешить» и должен согласиться** —
  установщик ставит `Shadow=1` (управление с согласием) в
  `HKLM\SOFTWARE\Policies\Microsoft\Windows NT\Terminal Services`. Значения
  ключа: 1 — управление с запросом, 2 — управление без запроса, 3 — просмотр с
  запросом, 4 — просмотр без запроса. Вариант без запроса (2/4) и снятие
  UAC-фильтра мы **убрали** намеренно — на это среагировал SOC (см. ниже);
- `/control` в команде даёт управление; убери его для просмотра без управления.

Кнопка **free** в строке MEMORY просит агент освободить оперативку.

**Рабочее время.** Idle считается только в рабочие часы; вне их — статус
OFF-HOURS, и в логи простоя это не попадает. По умолчанию таймзона
`Asia/Baku`, часы 09:00–12:00 и 14:00–18:00. Поменять можно прямо на вкладке
**IDLE** (кнопка **✎ EDIT** у строки WORK HOURS) — сохраняется в `config.json`,
перезапуск не нужен. Чтобы время на шкале совпадало с рабочими часами, держи
сервер в той же таймзоне.

## Сервер

Подойдёт любая машина в сети: Windows, Mac или Linux. Нужен Python 3.9+
(или Docker).

**Windows.** Поставь Python с [python.org](https://www.python.org/downloads/),
при установке отметь **Add python.exe to PATH**. Потом в папке проекта:

```
run.cmd
```

Один раз открой порт в брандмауэре (cmd от администратора), иначе агенты не
достучатся:

```
netsh advfirewall firewall add rule name=hostwatch dir=in action=allow protocol=TCP localport=8765
```

**Mac / Linux:**

```bash
./run.sh
```

При первом запуске скрипт сам создаст `.venv` и поставит зависимости, дальше
просто запускает сервер. Остановить — `Ctrl+C`. Если обновились зависимости
(`server/requirements.txt`), удали папку `.venv` и запусти снова.

**Docker:** `docker compose up -d --build`.

Панель: `http://<IP сервера>:8765`. Данные хранятся в `server/data/` (при
Docker — в `data/`).

### Пароль

С самого сервера (`http://localhost:8765`) панель открывается без пароля. С
других устройств браузер спросит пароль (имя пользователя любое). Пароль
лежит в `server/config.json` (при Docker — `data/config.json`):

```json
{
  "password": "придумай-пароль"
}
```

Образец — `server/config.example.json`. Пароль подхватывается без
перезапуска. Пока файла нет, панель открыта только на сервере. Агентам пароль
не нужен: отчёты и скачивание агента работают без него. При запуске через
Docker пароль спрашивается и на самом сервере.

### Шифрование (TLS/https)

По умолчанию трафик идёт по http — в открытом виде по сети летят токен агента,
пароль дашборда и команды. В корпоративной сети это замечание SOC (см. в конце);
чтобы закрыть — включи https:

1. Сгенерируй самоподписанный сертификат под адрес(а), по которым агенты ходят
   на сервер (имя хоста и/или IP — каждый должен быть в сертификате):

   ```
   cd tools
   ./make-cert.sh hostwatch 192.168.31.6
   ```

   Получишь `hostwatch.crt` (публичный) и `hostwatch.key` (приватный, держи на
   сервере). На Windows тот же `openssl` есть в составе Git for Windows.
2. Укажи серверу пару через переменные окружения — `run.sh`/`run.cmd` передадут
   их uvicorn:

   ```
   export HOSTWATCH_TLS_CERT=/path/hostwatch.crt
   export HOSTWATCH_TLS_KEY=/path/hostwatch.key
   ```

   Для Docker — положи пару в `./certs/` и раскомментируй `HOSTWATCH_TLS_*` в
   `docker-compose.yml`.
3. Агенту ничего настраивать не нужно: `hostwatch-setup.exe` берёт `hostwatch.crt`
   из скачанного zip (сервер кладёт его туда сам, когда работает по https) и
   импортирует в **Trusted Root** каждого ПК. Дальше агент ходит по `https://…`
   со штатной проверкой сертификата. Адрес сервера при установке указывай с
   `https://` (например `-Server https://hostwatch:8765`).

Сертификат должен покрывать тот адрес, что в `server_url`/`-Server`: если
агенты ходят по имени `hostwatch`, в сертификате нужен `DNS:hostwatch`; по IP —
`IP:<адрес>`. Меняешь адрес — перевыпусти сертификат с нужным SAN.

### Сменить адрес сервера сразу на всех ПК

Добавь в `config.json` поле `server_url` — агенты получат новый адрес в ответе
на очередной отчёт и сами на него переключатся (адрес сохранится и в их
автозапуске):

```json
{
  "password": "...",
  "server_url": "https://hostwatch:8765"
}
```

Это работает для **планового** переезда, пока агенты ещё достукиваются до
текущего сервера. Если IP уже сменился внезапно (DHCP при перезагрузке) и
старый адрес мёртв, агентам некуда прийти за новым — поэтому лучше сразу дать
серверу **стабильный адрес** (статический IP, DHCP-резервация или имя хоста
вроде `https://hostwatch:8765`), тогда менять ничего не придётся. С https новый
адрес должен быть в сертификате (см. выше). Проверь новый адрес на одном ПК
(трей → **Change server**) прежде чем пушить на всех.

Настройки через переменные окружения: `HOSTWATCH_PORT` (8765),
`HOSTWATCH_IDLE_AFTER` (120 с), `HOSTWATCH_STALE_AFTER` (30 с).

## Агент (на каждом Windows-компьютере)

Это два отдельных файла:

- `hostwatch-agent.exe` — **резидент**: висит в трее, собирает метрики и шлёт
  отчёты. Больше ничего не делает — не ставит себя, не повышает права, не пишет
  в реестр, не удаляет файлы.
- `hostwatch-setup.exe` — **установщик**: ставит, перенастраивает и удаляет
  агент. Весь код, требующий админа (UAC, автозапуск в `HKLM`, права на папку,
  RDP-shadow, остановка старого агента), живёт здесь и выполняется один раз.

Такое разделение сделано потому, что поведенческие антивирусы (в т.ч.
Касперский) цепляются именно за «установочные» действия. У резидента их теперь
нет, поэтому к постоянно работающему агенту вопросов меньше. Это не гарантия
тишины: по-настоящему снимает жалобу **подпись exe** или добавление в
доверенные в консоли антивируса.

1. Открой панель в браузере на этом компьютере.
2. Нажми **⬇ DOWNLOAD AGENT** — скачается `hostwatch.zip` с обоими файлами.
3. Распакуй zip и запусти `hostwatch-setup.exe` (держи `hostwatch-agent.exe`
   рядом — установщик берёт его из той же папки).
4. Запусти установщик. Адрес сервера обычно уже вшит при сборке (см. «Как
   собрать агент»), и установщик ничего не спрашивает; если не вшит — спросит
   один раз (дальше агент помнит сам).

Установка требует прав администратора: `hostwatch-setup.exe` сам запросит UAC
(если отказать — ничего не ставится). Он кладёт оба exe в
`C:\ProgramData\Hostwatch`, прописывает в автозагрузку (`HKLM`)
`hostwatch-agent.exe` и запускает его. Дальше агент стартует вместе с Windows,
работает в фоне с точкой в трее (голубая — всё хорошо, красная — нет связи с
сервером), занимает ~15–25 МБ памяти. Меню иконки: **Set label…**,
**Open dashboard**, **Change server…**, **Debug console**, **Uninstall**,
**Exit**. Метку можно поменять и в панели (✎). **Uninstall** в трее запускает
`hostwatch-setup.exe -uninstall` (с запросом UAC).

#### Дебаг

**Работающий агент.** Трей → **Debug console** или из cmd:

```
"C:\ProgramData\Hostwatch\hostwatch-agent.exe" -debug
```

Откроется консольное окно с живым логом: каждый тик, полный отчёт и ответ
сервера со временем, получение токена, офлайн-буфер и бэкфилл, ошибки со
стеком. Это отдельный процесс-просмотрщик — закрыл окно или Ctrl+C, а агент
работает дальше как работал. Пока окно не открыто, агент ничего не пишет. Лог
виден только тому же пользователю на этом ПК (по сети недоступен).

**Установка.** `hostwatch-setup.exe` с ключом `-debug` ставит агент и печатает
каждый шаг в консоль. Из cmd в папке с распакованными файлами:

```
hostwatch-setup.exe -debug
```

После UAC откроется окно с шагами: сервер, права на папку, RDP-shadow, какие
старые агенты остановлены, автозапуск, копирование обоих exe в `ProgramData`,
запуск агента. Любой шаг, который упал, пишется с ошибкой. В конце — «Press
Enter to close», агент при этом уже работает. С `-Server` тоже работает:
`hostwatch-setup.exe -debug -Server http://IP:8765`. Удаление с логом —
`hostwatch-setup.exe -debug -uninstall`.

**Окно не появляется.** Если консоль открыть не удалось, установщик покажет
окно с ошибкой. Если не появилось вообще ничего:

1. Проверь версию во второй строке меню трея — должна быть **3.0** или новее.
2. Нажми **Debug console** и посмотри в Диспетчере задач, появился ли второй
   `hostwatch-agent.exe`.
3. Запусти `"C:\ProgramData\Hostwatch\hostwatch-agent.exe" -debug` из cmd.
4. Просмотр событий → Журналы Windows → Приложение: ошибки `.NET Runtime` или
   `Application Error`.

Тихая установка (для массовой раскатки): `hostwatch-setup.exe -Server
http://IP:8765` — без окон, поставит и запустит агент (рядом должен лежать
`hostwatch-agent.exe`). Удаление: пункт **Uninstall** в меню или
`hostwatch-setup.exe -uninstall`.

#### Для всех пользователей ПК

Агент всегда ставится на всех пользователей: стартует у **любого** вошедшего
(и инфо о пользователе обновляется при смене аккаунта). Установщик кладёт оба
exe в `C:\ProgramData\Hostwatch` и прописывает автозапуск `hostwatch-agent.exe`
в `HKLM` (а не в профиль пользователя). Варианты:

- вручную: двойной клик по `hostwatch-setup.exe` и подтвердить UAC;
- через GPO/логон-скрипт от SYSTEM: `hostwatch-setup.exe -Server http://IP:8765`
  (рядом должен лежать `hostwatch-agent.exe`).

При такой установке настройки (адрес сервера, метка, буфер офлайна) лежат в
`C:\ProgramData\Hostwatch` — **общие для всех пользователей**, а не в профиле;
папке выдаётся право записи для всех, и работает один агент на машину.
Пользователя для дашборда агент берёт из активной сессии (кто сейчас за ПК),
так что при смене аккаунта инфо обновляется.

Полное удаление делается от админа: пункт **Uninstall** в трее (виден только
админам) или `hostwatch-setup.exe -uninstall`.

Для запуска нужен `.NET Framework 4` — он есть в каждой Windows 10/11.

### Как собрать агент

Собранные exe **не лежат в репозитории** (`agent/*.exe` в `.gitignore`): их
собирают под конкретную сеть с уже вшитым адресом сервера. Собрать нужно на
любой Windows 10/11 встроенным компилятором C# (`.NET Framework 4`) — Visual
Studio и .NET SDK не нужны. На Mac/Linux собрать нельзя.

1. Скопируй папку `agent/` на Windows-машину (удобнее всего — на сам сервер,
   тогда IP подхватится сам).
2. Запусти сборку, передав адрес сервера — он **вшивается** в оба exe, чтобы
   агент ставился без `-Server`:

   ```
   cd agent
   build.cmd                     автоопределить IP этой машины, порт 8765
   build.cmd 192.168.31.6        этот IP, порт 8765  -> http://192.168.31.6:8765
   build.cmd 192.168.31.6 9000   этот IP и порт
   build.cmd https://hostwatch:8765   полный URL как есть (так задают https)
   ```

   `build.cmd` пишет вшитый адрес в `hostwatch-build.cs` (git-ignored,
   пересоздаётся каждую сборку) и собирает `hostwatch-agent.exe` и
   `hostwatch-setup.exe`. Вшитый адрес — лишь значение по умолчанию: `-Server`,
   трей → **Change server** и `server_url`-пуш его перебивают. На 32-битной
   Windows путь к `csc.exe` — без `64`; `build.cmd` это учитывает сам.
3. Проверь: запусти `hostwatch-setup.exe` (без аргументов — адрес уже вшит).
   Появится точка в трее, а компьютер — на дашборде. Трей → **Debug console**
   открывает окно с живым логом; после закрытия окна точка остаётся.
4. Положи оба собранных exe в `agent/` **на сервере** (откуда он раздаёт zip) —
   через git они больше не едут. Если собирал не на сервере, скопируй их туда.

Нужна Windows 10/11 (PowerShell 5.1 встроен — им `build.cmd` определяет IP).

## Демо

Чтобы посмотреть панель без настоящих агентов (или сделать скриншоты):

```
run.cmd demo      (Windows)
./run.sh demo     (Mac / Linux)
```

Запустится выдуманный офис из 8 компьютеров с историей за пару месяцев. В демо-режиме
ничего не сохраняется, настоящие данные не затрагиваются.

## Проверить кнопку «free»

Чтобы искусственно нагрузить память на ПК и проверить освобождение, запусти
на этом компьютере `tools/hog.ps1` — он держит ~4 ГБ в оперативке:

```
powershell -ExecutionPolicy Bypass -File hog.ps1
```

Запускай **под тем же пользователем**, что и агент (тогда агент почистит без
прав администратора; если агент работает с правами админа — почистит и чужие
процессы). Порядок:

1. На дашборде на карточке этого ПК **MEMORY** подрастёт на ~4 ГБ (за пару секунд).
2. Нажми **free** на той же карточке.
3. Через 1–2 секунды used снова упадёт — агент сбросил рабочие наборы, страницы
   ушли в standby (считаются свободными).
4. Enter в окне PowerShell — освободить тестовую память.

`$gb` в скрипте подстрой под объём ОЗУ (на 8 ГБ ставь 3–4, не больше).

## Как это устроено и как обновлять

Памятка на будущее: что где лежит, как собирать и как не запутаться в git.

### Структура

- `server/app.py` — сервер (FastAPI): приём отчётов, API, раздача дашборда и
  агента, история, команды (free RAM), бэкфилл, пуш адреса.
- `server/static/{index.html, app.js, style.css}` — дашборд.
- `server/demo.py` — выдуманный офис для демо/скриншотов (`HOSTWATCH_DEMO=1`).
- `agent/hostwatch-agent.cs` — **исходник** резидентного агента (C#).
- `agent/hostwatch-setup.cs` — **исходник** установщика (C#).
- `agent/hostwatch-common.cs` — общий код обоих (JSON, конфиг, дебаг, пути, версия).
- `agent/hostwatch-{agent,setup}.exe` — **собранные** exe (не в git, собираются
  под сеть с вшитым адресом; кладутся в `agent/` на сервере, он их раздаёт одним zip).
- `agent/build.cmd` — сборка обоих exe из исходников (на Windows), вшивает адрес.
- `tools/make-cert.sh` — генерация самоподписанного TLS-сертификата для сервера.
- `tools/hog.ps1` — скрипт для теста кнопки free.
- `server/config.json` — пароль дашборда, рабочие часы, `server_url` (не в git).

### Как меняется агент

1. Правишь исходник (версия — в `Build.Version` в `hostwatch-common.cs`, одна на
   оба exe).
2. На Windows-машине (удобнее — на сервере) запускаешь `agent/build.cmd` с
   адресом сервера → получаешь свежие exe с вшитым адресом (см. «Как собрать агент»).
3. Кладёшь оба exe в `agent/` на сервере (в git они не едут — `.gitignore`).
4. Клиенты получают новую версию при переустановке (скачали zip с дашборда →
   запустили `hostwatch-setup.exe`; он останавливает старый агент и ставит
   новый). Адрес сервера можно сменить централизованно через `server_url` в
   `config.json` — см. выше.

Сервер отдаёт файлы с диска, поэтому после замены exe или правок дашборда
отдельная пересборка не нужна — только перезапуск сервера для нового кода
`app.py`.

### Статика дашборда (кэш)

Ссылки на `app.js`/`style.css` в `index.html` идут с версией `?v=N`. **Меняешь
`app.js` или `style.css` — увеличь N** (во всех ссылках), иначе у людей
останется старая версия из кэша браузера. После этого достаточно обычного
обновления страницы.

### Git: Mac + Windows

Исходник ты правишь на Mac, собираешь на Windows. Теперь exe в git **не
коммитятся** (`agent/*.exe` в `.gitignore`) — конфликтов по бинарникам больше
нет, расходятся только `.cs`. Если `git push` пишет `non-fast-forward`:

```
git pull --no-rebase
```

Чтобы `git pull` не переспрашивал про стратегию — один раз:
`git config pull.rebase false`.

Правило: **исходник (`.cs`) — главное, exe — артефакт**. После правок пересобери
оба exe на Windows (`build.cmd` с адресом сервера) и положи в `agent/` на
сервере — в репозиторий они не едут.

## Безопасность (замечания SOC 2ГИС)

SOC управляющей компании проверил инструмент (22.10.2026) и признал легитимным,
но дал два замечания. Что сделано:

- **Сервер — единая точка контроля.** Кто получит доступ к серверу, дотянется
  до подключённых хостов. Поэтому: держи сервер в LAN и под паролем дашборда;
  установщик больше **не ослабляет UAC** (`LocalAccountTokenFilterPolicy`) и
  делает RDP-shadow только **с согласия** пользователя (`Shadow=1`), а не молча.
- **Трафик по http.** Включи **TLS** (раздел «Шифрование» выше) — тогда токен
  агента, пароль дашборда и команды шифруются.

Остаётся по проекту: централизованный пуш адреса (`server_url`) переводит весь
парк на другой сервер — это мощный рычаг, держи доступ к `config.json` и серверу
ограниченным.
